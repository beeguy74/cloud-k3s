# Cloud-1 subject checklist

Derived from `cloud.en.subject.pdf` (Cloud-1, "Automated deployment of Inception", version 9).
Each item quotes or closely paraphrases the subject; **Verify** lines describe how to prove it at the defense.

## 1. Core goal (Introduction)

- [ ] Site and its Docker infrastructure are deployed on an instance from a cloud provider.
- [ ] Each process has its own container; Inception images are not just reused as-is.
  - Verify: `docker compose ps` shows one service per process (web server, PHP-FPM, database, phpMyAdmin).
- [ ] Every deployment stage is automated (Ansible suggested).
- [ ] Several services run in parallel: WordPress, phpMyAdmin and a database.

## 2. Mandatory part

### Automation and target host

- [ ] Deployment is fully automated: a working site equivalent to Inception comes from the script alone.
  - Verify: from a fresh host, one `ansible-playbook` run gives a working WordPress with no manual steps.
- [ ] A simple WordPress site is installed on an instance.
- [ ] The script runs assuming only an Ubuntu 22.04 LTS-like OS with an SSH daemon and Python installed.
  - Verify: target is a freshly created Ubuntu 22.04 cloud instance; nothing is pre-installed by hand.
- [ ] The Ansible code is portable: it deploys to a fresh instance, not only the development one.
  - Verify: no hard-coded IPs, users or hostnames in roles; only the inventory changes between instances.
- [ ] The site can be deployed on several servers in parallel.
  - Verify: inventory with 2+ hosts (`cloud1-a`, `cloud1-b`); one run deploys all of them.
- [ ] The installation code is idempotent: running it several times gives the same working result.
  - Verify: a second playbook run ends with `changed=0` and the site still works.

### Containers and services

- [ ] Applications run in separate containers that can talk to each other (1 process = 1 container).
- [ ] Services are WordPress components installed by you (for example phpMyAdmin, MySQL/MariaDB).
- [ ] The repository contains a `docker-compose.yml`.
- [ ] The SQL database works with both WordPress and phpMyAdmin.
  - Verify: log into phpMyAdmin and see the WordPress tables; WordPress admin login works.
- [ ] Official Docker images are allowed (image optimisation is encouraged, not required).

### Persistence and reboot

- [ ] The site restarts by itself after a server reboot.
  - Verify: `sudo reboot`; the site comes back without manual action.
- [ ] All site data survives a reboot: images, user accounts, articles.
  - Verify: create a post with an uploaded image and a new user, reboot, check that all of it is still there.

### Network, security and TLS

- [ ] Public access is limited and secure (for example, the database cannot be reached from the internet).
  - Verify: `nc -zv <host> 3306` from outside fails.
- [ ] Only ports 80 (HTTP), 443 (HTTPS) and 22 (SSH) can be reached from outside; all others are blocked.
  - Verify: `nmap -p- <host>` from outside lists only 22, 80 and 443.
- [ ] The server uses TLS when possible.
  - Verify: `curl -v https://<host>` completes a TLS handshake (Let's Encrypt certificate for the domain).
- [ ] The server sends each requested URL to the right site.
  - Verify: the WordPress URL serves WordPress and the phpMyAdmin URL serves phpMyAdmin.

### Code quality and secrets

- [ ] The Ansible code is split into relevant roles for maintainability.
- [ ] The code contains NO hard-coded secrets (for example a database password written in the code).
  - Verify: `git grep -iE 'password|secret|token'` finds only variable names or vault references, and the secrets file is encrypted or git-ignored.

## 3. AI usage (Chapter II)

- [ ] AI use is documented openly, and the README says which parts were generated by AI tools.
- [ ] Every design decision can be explained and defended without relying on AI.

## 4. Cost and cloud responsibility (Chapters III and V)

- [ ] Servers and services are sized sensibly and fit the free tier or student credits where possible.
- [ ] Deployed services are stopped when not in use; no forgotten servers or looping tasks.
- [ ] No keys or credentials are committed to the public repository (including cloud `openrc.sh` files and SSH private keys).
- [ ] You know the provider's terms and the billing risks of the credits you use.

## 5. Submission and defense (Chapter VI)

- [ ] All work is in the Git repository; folder and file names are double-checked.
- [ ] There is no bonus part; a basic WordPress site is enough.
- [ ] Optional but appreciated: a memorable domain name (for example DuckDNS) that serves the site over HTTPS.
- [ ] At the defense, log into the cloud provider account as root or owner with your own email or login.
  - Subject: "The student must connect as root using their email address or login as the root account. Otherwise, the case should be considered as a cheating attempt and the defense will stop."
